> Phase 1 — วิภูอนันต์ รีสอร์ท (Viphuanan Resort) Accounting & Capital Planning System
> สถานะเอกสาร: **ร่างเพื่อขอการยืนยัน** (รายการที่ต้องยืนยันอยู่ในไฟล์ 07)

| หัวข้อ | ข้อมูล | หมายเหตุ |

| เป้าหมาย | ทุนเปิดร้านสะดวกซื้อ 2,000,000 บาท | เก็บเป็นข้อมูลใน `capital_goals.target_amount` ไม่ฝังในโค้ด |

- กฎที่ยืนยันกับรีสอร์ตแล้วในแอปเดิม เช่น คำนวณเงินเป็นสตางค์, รายการที่ยืนยันแล้วห้ามลบ, สลิปซ้ำตรวจจากเลขอ้างอิง, ยกเลิกการจองคืนเงิน 50% — จะต้องยืนยันอีกครั้งว่ายังใช้กับระบบใหม่หรือไม่

## 1.2 ระบบต้องตอบคำถาม 8 ข้อ — ตอบจากอะไร

| # | คำถาม | ตอบจาก | เงื่อนไขที่ทำให้ตัวเลข "เชื่อได้" |
|---|---|---|---|
| 1 | รายได้จริงเท่าไร | `revenue_entries` สถานะ VERIFIED ตามวันที่ให้บริการ → ลงบัญชีรายได้ → `v_pnl_monthly.revenue` | งวดต้องเป็น FINAL (ปิดแล้ว) จึงเรียกว่ายืนยันแล้ว |
| 2 | เงินรับเข้าจริงเท่าไร / ค้างรับอะไร | `payments` VERIFIED ตามวันที่รับเงิน; ค้างรับ = `v_folio_balances.balance > 0` | เงินรับต้องจับคู่กับรายการธนาคารแล้ว (`v_book_reconciliation_status = MATCHED`) หรือเป็นเงินสดที่นับแล้ว |
| 3 | ค่าใช้จ่ายจริงมีอะไร | `expenses` VERIFIED ตามวันที่เกิด แยกหมวด; การจ่ายจริงใน `expense_payments` | เฉพาะหมวดที่ treatment เป็นค่าใช้จ่าย (ไม่รวมซื้อสินทรัพย์ ถอนเงินเจ้าของ ชำระเงินต้น) |
| 4 | กำไร/ขาดทุนเท่าไร | `v_pnl_monthly` (อ่านจากสมุดบัญชีคู่) | แสดง "กำไรสุทธิ (ยืนยันแล้ว)" เฉพาะ `completeness = FINAL`; อื่นๆ เป็น "เบื้องต้น" หรือ "ข้อมูลไม่ครบ" |
| 5 | เงินสด/เงินฝากที่ตรวจสอบแล้ว | `v_verified_cash` = ยอดจาก statement หรือการนับเงินสดล่าสุด เทียบยอดตามบัญชี | แสดงวันที่ของยอดและผลต่าง; ยอดเก่าเกินกำหนดต้องเตือน |
| 6 | ต้องกันเงินไว้เท่าไร | ภาระ = เงินรับล่วงหน้าของลูกค้า + เจ้าหนี้ค้างจ่าย + ค่าคอม OTA ค้างจ่าย + ประมาณการภาษีที่ยังไม่จ่าย + ค่างวดหนี้ N เดือน + เงินสำรองรีสอร์ต | ทุกองค์ประกอบมาจากรายการ VERIFIED และนโยบายที่เจ้าของยืนยัน (`capital_goals.policy_confirmed_by_owner`) |
| 7 | จัดสรรเป็นทุนได้เท่าไร | สูตร R20 (ข้างล่าง) | ติดลบ = 0 พร้อมบอกว่าขาดเท่าไร |
| 8 | ถึง 2,000,000 เมื่อไร | สูตร R21 ต่อ scenario | ใช้เงินส่วนเกินหลังหักภาระจากงวดที่ปิดแล้ว; ถ้ายังไม่มีงวดปิด ใช้ประมาณการเจ้าของพร้อมป้าย "ยังไม่ตรวจสอบ" |

## 1.3 นิยามที่ระบบใช้ (ห้ามปนกัน)

| คำ | ความหมายในระบบ | ตาราง/วันที่ที่ใช้ |
|---|---|---|
| **รายได้ (Revenue)** | มูลค่าบริการที่ให้แล้ว รับรู้ตามคืนที่เข้าพัก/วันที่ให้บริการ | `revenue_entries.service_date` |
| **เงินรับ (Receipt)** | เงินที่ลูกค้า/OTA จ่ายจริง | `payments.received_date` |
| **เงินเข้าธนาคาร (Bank credit)** | รายการในใบแจ้งยอดธนาคาร | `bank_transactions.txn_date` |
| **ลูกหนี้ (Receivable)** | folio ที่รายได้มากกว่าเงินที่จัดสรรมา | `v_folio_balances.balance > 0` |
| **เงินรับล่วงหน้า (Customer deposit)** | เงินที่รับก่อนให้บริการ หรือยังไม่ได้จัดสรร — เป็นหนี้สิน ไม่ใช่รายได้ และ **ไม่ใช่เงินที่นำไปลงทุนได้** | `balance < 0` + `v_payment_allocation_status.unallocated` |
| **ค่าใช้จ่าย (Expense)** | ต้นทุนที่เกิดขึ้นตามวันที่ในเอกสาร | `expenses.expense_date` |
| **การจ่ายเงิน (Disbursement)** | เงินออกจริง | `expense_payments.paid_date` |
| **กำไรทางบัญชี** | รายได้ − ค่าใช้จ่ายตามเกณฑ์คงค้าง | `v_pnl_monthly` |
| **กระแสเงินสด** | เงินเข้า − เงินออกจริงของบัญชีเงิน | journal lines ของบัญชีเงินสด/ธนาคาร (Phase 5) |
| **ตรวจสอบแล้ว (VERIFIED)** | มีผู้ตรวจรับรองพร้อมเวลา แก้ไม่ได้อีก | ทุกเอกสาร |
| **ยืนยันแล้ว (FINAL)** | ตัวเลขของงวดที่ปิดแล้ว (ปิดได้เมื่อข้อมูลครบ) | `v_period_completeness` |

## 1.4 Accounting Rules (กฎที่ระบบบังคับ)

คอลัมน์ "บังคับที่" — **DB** = constraint/trigger ในฐานข้อมูล (ทดสอบแล้วใน Phase 1), **App** = ตรรกะในแอป (ทดสอบใน Phase ที่ระบุ)

| รหัส | กฎ | บังคับที่ | ทดสอบ |
|---|---|---|---|
| R1 | เงินเก็บเป็น `NUMERIC(14,2)` บาท ห้าม float; คำนวณในแอปด้วย Decimal; ปัดเศษ ROUND_HALF_UP ที่ระดับเอกสาร; การแบ่งเงินให้เศษสตางค์ไปบรรทัดที่กำหนดเพื่อให้ผลรวมตรงเสมอ | DB + App | DB: `01` ✅ / App: Phase 3 |
| R2 | รายได้ค่าห้องรับรู้ **ต่อคืน** ตาม `service_date` (จาก Night Audit รายวัน); ค่ายกเลิก/No-show รับรู้วันที่เกิด | App (import) | Phase 2 |
| R3 | เงินรับบันทึกตามวันที่รับจริง เข้าบัญชีเงินที่ระบุ ห้ามอนุมานจากรายได้ | DB | `03`,`05` ✅ |
| R4 | **ยอดขาย ≠ ยอด Receipt ≠ ยอดเงินเข้าธนาคาร** — เชื่อมกันได้เฉพาะผ่าน `payment_allocations` และ `reconciliation_items` ที่คนยืนยัน | DB | `05`,`08` ✅ |
| R5 | เงินรับก่อนเข้าพัก/ยังไม่จัดสรร = เงินรับล่วงหน้า (หนี้สิน) | DB (view) | `05` ✅ |
| R6 | OTA แบบ Hotel Collect: ลูกค้าจ่ายเรา, ค่าคอมเป็นค่าใช้จ่ายในงวดที่เข้าพัก (ตั้งเจ้าหนี้), จ่ายใบแจ้งหนี้ OTA = **ล้างหนี้** ไม่ใช่ค่าใช้จ่ายซ้ำ | DB | `06`,`07` ✅ |
| R7 | OTA แบบ OTA Collect: รายได้บันทึก **ยอดเต็ม**, ลูกหนี้ OTA, payout สุทธิจัดสรรเข้า folio, ค่าคอมที่ถูกหักลดลูกหนี้ของ folio | DB | `05` ✅ (ต้องยืนยันว่า PMS บันทึกยอดเต็มหรือสุทธิ — ไฟล์ 07) |
| R8 | ค่าธรรมเนียมบัตร/QR: `payments.fee_amount`; เงินที่เข้าธนาคาร = amount − fee | DB | `08` ✅ |
| R9 | ค่าใช้จ่ายบันทึกตามวันที่ในเอกสาร; การจ่ายบันทึกแยก (จ่ายบางส่วนได้); ยอดค้าง = total − WHT − ที่จ่ายแล้ว | DB | `06` ✅ |
| R10 | ซื้อสินทรัพย์ / โอนระหว่างบัญชี / ถอนเงินเจ้าของ / ชำระเงินต้น / นำส่ง VAT-WHT / จ่ายหนี้ค่าคอม **ไม่ใช่ค่าใช้จ่าย** — กำหนดโดย `expense_categories.treatment` ที่ต้องตรงกับประเภทบัญชี | DB | `06`,`07` ✅ |
| R11 | ค่าคอม OTA และค่าเสื่อมราคาเป็นบัญชีระบบ ห้ามบันทึกผ่านใบสำคัญจ่าย (กันนับซ้ำ) | DB | `06` ✅ |
| R12 | VAT: บันทึกเมื่อ `tax_profiles.vat_status = REGISTERED` ที่นักบัญชียืนยันเท่านั้น; ระบบไม่สมมติอัตรา | DB (โครงสร้าง) + App | `10` ✅ / Phase 6 |
| R13 | รายงานนับเฉพาะเอกสาร VERIFIED; DRAFT แสดงแยกเป็น "รอตรวจสอบ" | DB (views) | `05`,`06`,`10` ✅ |
| R14 | VERIFIED แก้/ลบไม่ได้ ยกเลิกได้เมื่อมีเหตุผล แล้วบันทึกใหม่; VOIDED ถาวร | DB | `03` ✅ |
| R15 | งวดที่ปิดแล้วล็อกทุกตาราง การแก้ไขให้บันทึกรายการปรับปรุงในงวดที่เปิดอยู่; เปิดงวดใหม่ต้องมีผู้เปิด เวลา เหตุผล และทำย้อนทีละงวด | DB | `09` ✅ |
| R16 | ป้ายความครบถ้วน: **FINAL** (ปิดงวด), **PRELIMINARY** (ไม่มีปัญหาค้างแต่ยังไม่ปิด), **INCOMPLETE** (มีปัญหา) — ทุกหน้ารายงานต้องแสดง | DB (view) + App | `07`,`09` ✅ |
| R17 | ปิดงวดได้เมื่อไม่มีปัญหาค้าง: ทุกวันมีรายงานรายได้, ทุกบัญชีธนาคารมี statement ครบเดือน, ยอดปลายเดือนยืนยันแล้วและเท่ายอดบัญชี, รายการธนาคาร/เงินรับ/การจ่ายจับคู่ครบ, ไม่มี DRAFT, ไม่มีค่าคอมที่ยังเป็นค่าประมาณ, ไม่มีไฟล์นำเข้าค้างตรวจ | DB | `09` ✅ |
| R18 | นำเข้าไฟล์เดิมซ้ำไม่ได้ (SHA-256); แถวที่ key เดิม commit ซ้ำไม่ได้; เลขอ้างอิงต้นทางเดียวกันเป็นเอกสารซ้ำไม่ได้; key เดิมแต่ค่าเปลี่ยน → CONFLICT ให้คนตัดสิน | DB + App | `04` ✅ / Phase 2 |
| R19 | ไฟล์ที่ยอดรวมไม่ตรงรายงานต้นฉบับ COMMIT ไม่ได้; ข้อมูลดิบเก็บไว้ไม่แก้ | DB | `04` ✅ |
| R20 | **เงินที่จัดสรรเป็นทุนได้** = max(0, เงินสด/ฝากที่ตรวจสอบแล้ว − เงินกองทุนที่มีอยู่แล้ว − เงินรับล่วงหน้า − เจ้าหนี้ค้างจ่าย − ค่าคอมค้างจ่าย − ประมาณการภาษีที่ยังไม่จ่าย − ค่างวดหนี้ N เดือนข้างหน้า − เงินสำรองรีสอร์ต) | App | Phase 7 (กรณีทดสอบในไฟล์ 08) |
| R21 | **จำนวนเดือนถึงเป้า** = ceil(ยอดที่ยังขาด ÷ เงินส่วนเกินที่จัดสรรได้ต่อเดือน); เงินส่วนเกินต่อเดือน = (เฉลี่ยรายได้ − ค่าใช้จ่ายดำเนินงาน − ภาษีที่ต้องกัน − ค่างวด − เงินถอนเจ้าของ จากงวด FINAL ย้อนหลัง N เดือน) ปรับตาม scenario × สัดส่วนจัดสรร; ถ้า ≤ 0 → "ไม่ถึงเป้าภายใต้สมมติฐานนี้" | App | Phase 7 |
| R22 | ภาษีเป็น "ประมาณการ" จนกว่าจะยื่นแบบ (FILED) ห้ามแสดงเป็นยอดภาษีที่ต้องชำระ; ประมาณการที่ยื่น/จ่ายแล้วแก้ไม่ได้ | DB + App | `10` ✅ / Phase 6 |
| R23 | กระทบยอดธนาคาร **ไม่สร้างรายรับรายจ่ายเอง**; ระบบเสนอได้แต่คนต้องยืนยัน; ผลต่างต้องมีเหตุผล | DB | `08` ✅ |
| R24 | วันที่เก็บเป็น ค.ศ. (ISO); แสดงผลแบบไทย `วว/ดด/ปปปป` พ.ศ. (เช่น 09/10/2569) เลือก ค.ศ. ได้; ไฟล์นำเข้าที่ปี > 2400 ให้ลบ 543; ตัดวันตามเวลา Asia/Bangkok | App | Phase 2 |
| R25 | ทุกการสร้าง/แก้/ยืนยัน/ยกเลิก/อนุมัติ/ปิดงวด บันทึก Audit Log อัตโนมัติพร้อมผู้ทำและเหตุผล; Audit Log แก้/ลบไม่ได้; รหัสผ่านไม่ถูกบันทึก | DB | `02` ✅ |

## 1.6 Non-functional requirements

- **ภาษา/รูปแบบ**: UI ภาษาไทยเป็นหลัก มีภาษาอังกฤษ; THB แสดง `฿1,234.50`; วันที่แบบไทย (R24)
- **อุปกรณ์**: responsive ใช้ได้บนมือถือ (หน้าอัปโหลด/บันทึกรายการต้องใช้มือเดียวได้) และคอมพิวเตอร์ (หน้ากระทบยอด/รายงาน)
- **ความปลอดภัย**: Login + RBAC + MFA สำหรับ OWNER/ACCOUNTANT, ไม่มี secret ใน frontend, ไฟล์หลักฐานใน private storage (ไฟล์ 02)
- **ความถูกต้อง**: กฎ R1–R25; ทุกตัวเลขบนหน้าจอย้อนกลับไปหาเอกสารและไฟล์ต้นฉบับได้ (import_row_id → imported_files)
- **ความพร้อมใช้งาน/สำรองข้อมูล**: สำรองอัตโนมัติรายวัน เข้ารหัส เก็บนอกเครื่อง, ทดสอบกู้คืนรายเดือน (ทดสอบเบื้องต้นแล้วใน Phase 1 — ไฟล์ 08)
- **ข้อมูลส่วนบุคคล (PDPA)**: เก็บชื่อแขกเท่าที่จำเป็นต่อการจับคู่ folio ไม่เก็บเบอร์โทร/เลขบัตร/ที่อยู่ในระบบนี้
- **ประสิทธิภาพ**: 15–30 ห้อง ≈ 5,000–15,000 แถวรายได้ต่อปี — views คำนวณสดได้; ถ้าช้าจึงทำ materialized view (วัดใน Phase 8)

## 1.7 นอกขอบเขต Phase นี้ / สมมติฐาน

- ไม่ทำระบบจองห้องหรือ channel manager (HotelRunner ทำอยู่แล้ว)
- ไม่ยื่นภาษีแทนนักบัญชี และไม่กำหนดอัตราภาษีเอง
- สกุลเงินเดียว (THB); ถ้า OTA จ่ายเป็นสกุลอื่น ต้องออกแบบเพิ่ม
- บัญชีของร้านสะดวกซื้อในอนาคตรองรับด้วย `properties` แยก แต่ยังไม่ออกแบบรายละเอียด
